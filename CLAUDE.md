# my-ai-skills

Gustavo Eklund's agent skills. One skill per directory, versioned as a single
collection, linted, and shipped as a Claude Code plugin.

Everything here is written in English: skills, documentation, changelog
entries, commit messages and code comments.

## Layout

```
skills/<bucket>/<skill-name>/SKILL.md
```

| Bucket | Holds | Promoted |
| --- | --- | --- |
| `engineering/` | daily code work | yes |
| `productivity/` | daily non-code workflow | yes |
| `meta/` | skills about maintaining this repository | no |

**Promoted** buckets are the ones that ship: every skill in them has an entry
in `.claude-plugin/plugin.json`'s `skills` array and a row in `README.md`.
`meta/` skills ship in neither. They load as project skills through the
committed `.claude/skills/` symlinks, so they are reachable inside this
repository and nowhere else.

A skill's `name` must equal its directory name. Names are unique across the
whole repository, regardless of bucket. Moving a skill between buckets does not
break installs, because every consumer sees only the leaf name.

## Two kinds of skill

**Content skills** hold instructions. Gerund name (`grilling`,
`reviewing-migrations`). Model-invocable by default.

**Alias skills** are entry points and hold no instructions. Imperative name
that reads like a command (`grill-me`). Their body is a single line delegating
to a content skill, they set `disable-model-invocation: true`, and they declare
`metadata.delegates-to`.

An alias exists only for a reason: an imperative name that gets typed, or a
second skill that composes the same content. Without one of those, the content
skill is already reachable as `/<name>` and the alias only costs context, since
every description is preloaded into the system prompt.

`disable-model-invocation` is a Claude Code extension, not part of the Agent
Skills spec. Alias skills are therefore Claude-Code-only and cannot be uploaded
to claude.ai or the Skills API.

## Frontmatter contract

Required on every skill:

- `name` — lowercase letters, digits and hyphens, at most 64 characters, equal
  to the directory name, containing neither `claude` nor `anthropic`.
- `description` — third person, at most 1024 characters, stating both what the
  skill does and when to reach for it. This is the field Claude matches
  against, and the field the overlap check compares.

Repository bookkeeping lives under `metadata`, which the Agent Skills spec
defines as free-form and every harness ignores:

- `metadata.delegates-to` — the content skill this alias forwards to. Its
  presence is what makes a skill an alias.
- `metadata.boundary` — one sentence naming the nearest skill and the rule that
  divides them. Required once the overlap check flags a pair.
- `metadata.source` — attribution when the method came from someone else.
- `metadata.upstream` and `metadata.upstream-version` — the repository a
  vendored skill's text came from, and the release it was taken at. They go
  together, and they are what `npm run vendor:check` reads.

Everything else must be a field Claude Code actually supports. `npm run lint`
rejects unknown keys, which is how typos get caught.

## Vendored skills

A skill whose text came from another repository declares `metadata.upstream`
and `metadata.upstream-version`, and carries that project's `LICENSE` in its own
directory. The lint enforces both: vendoring a substantial portion of someone
else's work without shipping their notice is the failure worth catching.

Keep the vendored body byte-identical to upstream and confine local changes to
the frontmatter. A modified body cannot be diffed against a new release, which
is the whole reason the version is recorded.

`npm run vendor:check` asks each upstream for its latest release and reports
what has fallen behind. It stays out of CI: it needs the network, and a new
upstream release is news to act on, not a build to break. To update one,
re-vendor the body, bump `metadata.upstream-version`, re-run the checks, and
record it in the changelog under `Changed`.

## Per-skill validators

A skill with invariants this repository's lint cannot know about ships
`scripts/validate.ts` in its own directory. `npm run lint` discovers it, runs
it, and reports a non-zero exit as its own errors.

Use it for rules that are true of one skill and meaningless elsewhere: a
numbered sequence that must have no gaps, cross-references that must resolve, a
line budget tighter than the repository's. Rules that would apply to any skill
belong in `scripts/lint.ts` instead.

## Adding or changing a skill

Follow [`authoring-skills`](skills/meta/authoring-skills/SKILL.md). The short
version: state the new skill's trigger surface in one sentence, compare it
against every row above, and decide between extending an existing skill,
carving a stated boundary, or extracting shared content. Then run
`npm run check`.

## Versioning

One version for the whole collection, in `package.json`, mirrored into
`.claude-plugin/plugin.json` and the top of `CHANGELOG.md`. The lint fails if
the three disagree.

- **MAJOR** — a skill is removed or renamed, or its invocation contract changes
  (model-invocable becomes user-only, or the reverse). Anything that breaks an
  existing symlink or a command already in muscle memory.
- **MINOR** — a skill is added, or an existing skill gains a capability.
- **PATCH** — wording, corrections, clarifications that leave behaviour intact.

Reclassifying a skill's bucket is PATCH, since consumers never see the bucket.

## Changelog

[Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Every change to
`skills/` lands under `## [Unreleased]` in the same commit, in the right
section (`Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security`).
Entries name the skill in backticks and say what changed for the user of the
skill, not what changed in the file.

The section a change goes into decides the next version number, so choose it
against the MAJOR/MINOR/PATCH rules above rather than by feel.

## Releasing

`npm run release -- <major|minor|patch>` does the whole cut: bumps
`package.json` and `.claude-plugin/plugin.json`, turns `[Unreleased]` into a
dated version section with its comparison link, commits, and tags `vX.Y.Z`.
Pushing the tag triggers `.github/workflows/release.yml`, which opens the
GitHub Release with that changelog section as the body.

Never edit released changelog sections. Corrections go in a new version.

## Checks

`npm run check` runs both, and CI runs it on every push and pull request:

- `npm run lint` — frontmatter validity, name and uniqueness rules, alias
  rules, body length, link resolution, reference depth, plugin manifest
  membership, version agreement, changelog shape, and description overlap
  between content skills.
- `npm run index:check` — fails when the generated index no longer matches the
  filesystem. An index that lies is worse than no index.

`npm run vendor:check` is run by hand, for the reason given above.

Run `claude plugin validate . --strict` after touching anything in
`.claude-plugin/`. It stays out of CI because the CLI is not available there.
